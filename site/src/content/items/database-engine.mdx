## Context

A database stores data in fixed-size pages on disk and keeps some of them in memory. This course project implemented
those layers from scratch in C, each layer using only the one below it. A B+-tree index followed as the team's final
assignment.

## Approach

Each layer was checked against the course's test programs before the next one used it. The buffer manager tracks which
pages are in use, which have changed and which were used least recently. The record manager stores fixed-size records
in slotted pages and reaches the disk only through the buffer manager.

<More label="How each layer works">
- **Storage manager.** Page files of a fixed page size, with create, open, close and destroy, and reading and writing
  by block.
- **Buffer manager.** Each frame records its page number, how many clients are using it (the fix count), whether it has
  changed, and when it was last used. When the pool is full, FIFO or LRU replacement picks a page to evict. Frames in
  use are never evicted, and a request fails with an error when every frame is in use. Changed pages are written back
  before eviction, and the pool counts its disk reads and writes.
- **Record manager.** The first page of a table's file holds the table's metadata and schema. Each data page starts
  with a header (total slots, occupied slots, next free page), followed by a bitmap of used slots and the fixed-size
  record slots. The table tracks the first page with free space, and a new page is added when that page fills. Records
  can be inserted, updated, deleted and read, and a scan returns only the records that match a condition.
</More>

## Contribution

- Implemented the storage manager's page-file handling and the buffer manager's pinning, FIFO and LRU replacement and
  write-back of changed pages, after designing the page-frame structure in written notes.
- Implemented the record manager's table creation, record insertion, update, deletion and conditional scan, with a
  slot bitmap and fixed-size slots in each page.
- Corrected memory leaks in the buffer manager's status arrays, and changed LRU's timestamps to a millisecond clock so
  that replacement worked on Linux.

<More label="Correctness checks and testing">
- **Test programs.** The buffer manager was checked with the course's tests of FIFO and LRU, which compare the pool's
  contents after each request. The record manager was checked with tests that create a table, insert, update, delete
  and read records, and run several scans at once.
- **Self-check on table creation.** After a table is created, the record manager reads its first two pages back and
  confirms that the stored metadata, schema and empty slot bitmap match what was written.
- **Memory.** The assignment treated memory leaks as errors. The dirty-flag and fix-count arrays were first allocated
  on every call; they are now allocated once with the pool and freed when it shuts down.
- **Pinned pages.** The pool refuses to shut down while any page is still in use, and every record operation releases
  the pages it pins.
</More>

## Lessons learned

- **Allocate once, free once.** Returning a newly allocated array from every status call leaked memory. Tying each
  array to the pool's lifetime removed the leak and kept clean-up simple.
- **Each layer depends on the one below it.** The record manager's correctness rested on the buffer manager releasing
  pages properly, so a pinning mistake in the lower layer surfaced as a failure in the upper one.
