## Problem

A database has to move fixed-size pages between disk and memory, and store records inside those pages. We built those
layers from scratch in C, each using only the layer below it.

## Approach

<Flow
  label="The layers of the engine, bottom to top"
  steps={['Storage manager: page files on disk', 'Buffer manager: a pool of pages in memory', 'Record manager: tables in slotted pages', 'Scans filtered by a condition']}
/>

<More>
- **Storage manager.** Page files of a fixed page size, with create, open, close and destroy, and reading and writing
  by block.
- **Buffer manager.** Each frame tracks how many clients are using it, whether it has changed, and when it was last
  used. When the pool is full, FIFO or LRU replacement picks a page to evict, and changed pages are written back to
  disk first. The pool also counts its disk reads and writes.
- **Record manager.** Each page starts with a header (total slots, occupied slots, the next page with free space),
  followed by a bitmap of used slots and the fixed-size record slots. Pages with free space are chained together, and
  the table's schema is stored on its first page. Records can be inserted, updated, deleted and read, and scans return
  only the records that match a condition.


- Everything runs against the course's test programs, and memory leaks count as failures.
</More>

Before writing the buffer manager I worked the design out on paper. My first sketch left an open question: where
does each page frame keep its own state, such as whether it has been changed? My answer was an array of pointers,
one per frame, each to a small structure holding the page number, a dirty flag and a pointer to the page's data.
