## Context

The course's semester project was a small search engine with three parts: a crawler that collects pages, an indexer
that turns them into something searchable, and a query processor that ranks pages for a user's question.

<More label="The assignment and the data">
The report states the objective: download documents in HTML, convert them into an index, and return the top ten
documents for a query. The corpus was Wikipedia articles, collected by a spider from a single seed article. Wikipedia
pages are long and varied, so three short test documents with known content were used to check the index and the
ranking by hand.
</More>

## Approach

A Scrapy spider saves Wikipedia pages as HTML. An indexing script extracts and tokenises their text and stores, for
each word, the documents that contain it with TF-IDF weights. A Flask app weights the query in the same way, scores
only the pages that share a word with it, lists the top ten titles, and opens the page whose title the user enters.

<More label="How each part works">
- **Crawler.** The spider starts from a seed article, follows its links and saves each page as HTML under its title,
  with spaces replaced by underscores so that Flask can open the file later. A depth setting and a page limit are set
  in the source file; the report's test used a depth of 1 and 20 pages.
- **Indexing.** Each saved page is read, its text extracted with BeautifulSoup, lowercased and tokenised with NLTK, and
  only alphabetic words are kept. Term frequency is the word's count divided by the document's length, and inverse
  document frequency is the natural logarithm of the number of documents over the number that contain the word. Each
  word is stored with its documents and weights, and the index is saved as pickle files.
- **Search app.** The app rebuilds the index in memory when it starts. A query is tokenised and weighted the same way,
  and words absent from the index get weight zero. The ten best titles are shown, and the user types a title to open
  that page.
</More>

<More label="The scoring calculation">
Each word in each document gets a weight, and a document's score for a query is meant to add up the weights of the
words they share, divided by the document's length:

$$
w_{t,d} = \frac{\text{count}(t,d)}{|d|}\cdot \ln\frac{N}{\text{df}(t)}
\qquad
\text{score}(q,d) = \frac{1}{|d|}\sum_{t\in q\cap d} w_{t,q}\,w_{t,d}
$$

Here $|d|$ is the number of words in document $d$, $N$ the number of documents, and $\text{df}(t)$ the number of
documents that contain word $t$. The query weight $w_{t,q}$ uses the same formula with the query's length. This is a
length-normalised overlap, not cosine similarity, which divides by the lengths of both weight vectors instead.

For the query "pink rose", "rose" appears only in Temp1 and "pink" only in Temp3, so both have
$\text{idf} = \ln(3/1) = 1.099$. In Temp1, "rose" occurs twice in 29 words (weight 0.076); in Temp3, "pink" occurs
once in 31 words (weight 0.035). Temp1 ranks first. Words found in every document, such as "flower", get an idf of 0,
so they cannot tell documents apart.
</More>

## Lessons learned

The engine ran end to end: crawl, index, query and view. Of the report's three test queries, two came back in the
right order. Re-reading the code later showed why the third did not.

- **Check the order, not only that results appear.** For "ABC red Rose sour", Temp1 contains three of the four words,
  yet the engine ranked Temp2 first. Writing the expected ranking down before a test, and comparing it automatically,
  would have shown this.
- **Test each function alone.** The fault was in the scoring step, where a return inside a loop divided only one
  document's score by its length. A direct test of that function on two documents would have exposed it.
- **Keep full precision until the final display.** Term frequencies and weights were rounded to three decimals, so a
  word that occurs once in a page of more than about 2,000 words rounds to zero and drops out of the index.

<More label="What went wrong in the scoring step">
The scoring function first adds up the weight products for every document that shares a word with the query. It should
then divide each sum by that document's length, but the return statement sat inside the loop that does this, so only
the first document to receive a score was divided and the others kept their raw sums.

For "ABC red Rose sour" the first document to score was Temp1. Its sum of 0.0325 became 0.0011, while Temp2 (0.0026)
and Temp3 (0.0013) stayed undivided, so Temp1 fell to last place. With every score divided, the order would have been
Temp1, Temp2, Temp3.
</More>
